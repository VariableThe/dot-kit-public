# Active T3 launch and completion route

`runAndMonitor` is the required entry point for an authorized launch or follow-up in this workflow. It dispatches once and starts the exact-run event wait in the same awaited execution. Do not call the native launch/send directly and leave attachment of a watcher to a later model turn.

This is an executable caller integration, not a T3 server hook. It covers operations routed through it; it cannot intercept an arbitrary direct native-tool call. Installing files does not start a daemon. One native worker owns the invocation so its parent stays available.

## Files and installed layout

- `active-monitor.mjs`: authorized launch/send, recovery and immediate monitor handoff.
- `completion-core.mjs`, `completion-monitor.mjs`: pure validation, bounded event waits, immediate validated result reads.
- `completion-journal.py`: Python standard-library single-host store, private atomic snapshots, owner leases and fencing. No network or credentials.
- `exec-bridge.mjs`: adapter to the caller's existing shell tool and four existing native T3 callbacks.
- `active-runtime.js`: deterministic standalone execution-isolate bundle, generated by `node build-runtime.mjs`.

The supported local install layout is `$HOME/.local/share/dot-t3-monitor/`. The journal directory is `$HOME/.config/agent-kit/t3-completion`. Resolve HOME on the selected computer. Do not copy credentials or use another host's journal. Both reads and writes use the existing execution route; sandbox permission review is required when the runtime requires it.

## Actual invocation in the tools execution isolate

Load the exact installed `active-runtime.js` through the selected computer's file-read tool. Keep its source in the invocation/session; this is code, not the durable record. For example, `store('t3RuntimeSource', readResult.output)` after checking that the read succeeded and was not truncated.

In one awaited execution, construct the runtime and bridge, then run:

```js
const runtime = new Function('return (' + load('t3RuntimeSource') + '\n)')();
const bridge = runtime.createToolBridge({
  execCommand: tools.exec_command,
  toolMap: {
    t3_thread_launch: tools.CURRENT_T3_LAUNCH_TOOL,
    t3_thread_send: tools.CURRENT_T3_SEND_TOOL,
    t3_thread_wait: tools.CURRENT_T3_WAIT_TOOL,
    t3_thread_read: tools.CURRENT_T3_READ_TOOL,
  },
  journalPath: verifiedHome + '/.local/share/dot-t3-monitor/completion-journal.py',
  journalDirectory: verifiedHome + '/.config/agent-kit/t3-completion',
  // Only if required by the current runtime; never bypass a denial.
  persistenceOptions: approvedPersistenceOptions,
});
const result = await runtime.runAndMonitor({
  operationId: stableOperationId,
  owner: nativeWorkerIdentity,
  method: 'launch', // or 'send'; never inferred from a response
  args: authorizedNativeArguments, // verified environmentId and clientRequestId required
  context: {
    parentTask: parentTaskIdAsString,
    acceptanceCriteria: taskAcceptanceCriteria,
    startPosition: originalReadBoundary, // -1 for no prior items; never sent to T3
  },
  ...bridge,
  monitorOptions: {timeoutMs: 60000, maxWaits: 60},
});
```

Replace the four callback placeholders with tool names discovered in the current catalog for the verified connector. Discover schema and provider/model first. The wrapper does not authorize an action or choose a provider. Preserve all user account, model, spending and runtime restrictions. Do not use a personal ChatGPT/Codex provider merely because T3 lists it.

Use the runtime's supported execution continuation for a yielded invocation. Do not end/terminate the execution while it owns active work. Tool execution itself owns the wait, not an unawaited Promise. The wrapper uses the exact native response IDs and never retries a mutation automatically. The current native launch and send schemas support `clientRequestId`; retain it across any explicitly approved, reconciled retry.

## Ownership and recovery

The journal saves operation/request hashes, the request ID, parent task identifier, exact environment/thread/run IDs, original read boundary and progress metadata. It does not save prompts, replies, tokens or arbitrary URLs. Actual acceptance criteria remain in the parent task. The lease is refreshed at checkpoints and before reads; its default is five minutes. A replacement owner can claim an expired or explicitly released lease, and stale owners are fenced out.

For recovery, call `runAndMonitor` with the same operation ID, a current owner, `method:'resume'`, and the same bridge. Do not supply a new prompt or native mutation arguments. A known accepted run is observed again. Intent with a missing acceptance response returns `dispatch_uncertain`, without resending. Reconcile the existing request before any separately authorized retry, using the same client request ID and identical request arguments when the live interface supports it.

An execution budget ending returns `watch_incomplete`; keep ownership at the parent and resume this operation. An auth/permission error, pending approval/question, or broken journal is a blocker, not completion. Report the exact issue promptly and retain the unfinished record. Do not create replacement T3 work, widen access, or repair credentials as recovery.

While a thread has a live watcher lease, a separate send operation is rejected before dispatch. Ask the existing native watcher to stop its observation, await its release, and explicitly hand ownership to the follow-up operation. Do not interrupt T3 work merely to stop observation. This implementation serializes thread operations rather than attaching concurrent sends to one watcher. Reconcile the predecessor record after a deliberate handoff; a released record alone does not establish a new active owner.

A different settled `resultRun` is not silently adopted. After independently verifying continuation lineage, resume with `continuation:{verifiedResultRunIds:[exactId],evidenceRef:authoritativeResultReference}`. The proof reference is recorded. This outside-caller wrapper never claims ownership of T3 app-owned child wake subscriptions.

The store enables recovery but does not run it. If every caller is terminated, no unattended recovery is guaranteed unless a separately authorized scheduler is actually installed and verified. No scheduler, daemon, server callback or credential was created by this implementation.

## Parent review and delivery

`ready_for_review` means coherent final evidence is available, not that acceptance criteria passed or the user received it. The wrapper releases its lease and leaves `review_pending`. The parent verifies artifacts/tests, then uses the journal CLI to claim the operation with `method:'resume'` for delivery bookkeeping (do not rerun the monitor for this step):

1. `claim`: `{action:'claim',operationId,owner:parentOwner,method:'resume'}`. Retain the returned generation.
2. Before sending, `delivery` with `{operationId,owner,generation,state:'delivery_pending'}`.
3. After a confirmed accepted user-message send, `delivery` with `state:'delivered'` and its verified `receiptId` when available. An accepted send is not proof it was read.
4. If the send outcome is uncertain, record `delivery_uncertain`; do not retry blindly. Release the lease afterward.

The CLI accepts one JSON request on stdin, for example `python3 completion-journal.py --directory <verified-path>`. `read` and `list` are strictly read-only. Successful writes return `{record}`; failures return `{ok:false,error:{code}}` and exit 1. Delivery and connector-side read acknowledgments are separate.

## Verification

```sh
node build-runtime.mjs --check
node --test *.test.mjs
PYTHONDONTWRITEBYTECODE=1 python3 completion-journal.test.py
```

Tests cover pre-dispatch durability, uncertain responses, exact-run recovery, stale owners, cross-operation request-key reuse, same-thread contention, escaped native IDs, private atomic storage, generation fencing, bundle execution, continuation proof, pre-read identity checks, original cursor handling, delivery uncertainty and no unsolicited mutation. Live evidence and remaining limits belong in the validation report; offline tests are not evidence of an unattended daemon or successful user delivery.
