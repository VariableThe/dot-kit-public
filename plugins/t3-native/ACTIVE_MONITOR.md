# Active T3 launch and completion route

`runAndMonitor` is the required entry point for an authorized launch or follow-up in this workflow. It dispatches once and starts the exact-run event wait in the same awaited execution. Do not call the native launch/send directly and leave attachment of a watcher to a later model turn.

This is an executable caller integration, not a T3 server hook. It covers operations routed through it; it cannot intercept an arbitrary direct native-tool call. Installing files does not start a daemon. One native worker owns the invocation so its parent stays available.

## Files and installed layout

- `active-monitor.mjs`: authorized launch/send, recovery and immediate monitor handoff.
- `completion-core.mjs`, `completion-monitor.mjs`: pure validation, bounded event waits, immediate validated result reads.
- `completion-journal.py`: Python standard-library single-host store, private atomic snapshots, owner leases, fencing, read-only recovery inventory and explicit successor adoption. No network or credentials.
- `completion-journal-batch.py`: optional adjacent metadata batches over the same fenced journal store. The one-shot path remains the default.
- `exec-bridge.mjs`: adapter to the caller's existing shell tool and four existing native T3 callbacks.
- `active-runtime.js`: deterministic standalone execution-isolate bundle, generated by `node build-runtime.mjs`.
- `manifest.json`: SHA-256 inventory of this source, test and documentation set.

The supported local install layout is `$HOME/.local/share/dot-t3-monitor/`. The journal directory is `$HOME/.config/agent-kit/t3-completion`. Resolve HOME on the selected computer. Do not copy credentials or use another host's journal. Both reads and writes use the existing execution route; sandbox permission review is required when the runtime requires it.

## Actual invocation in the tools execution isolate

Load the exact installed `active-runtime.js` through the selected computer's file-read tool. Keep its source in the invocation/session; this is code, not the durable record. For example, `store('t3RuntimeSource', readResult.output)` after checking that the read succeeded and was not truncated.

In one awaited execution, construct the runtime and bridge, then run:

```js
const runtime = new Function('return (' + load('t3RuntimeSource') + '\n)')();
const bridge = runtime.createToolBridge({
  execCommand: tools.exec_command,
  toolMap: {
    t3_thread_launch: tools.CURRENT_T3_LAUNCH_TOOL,
    t3_thread_send: tools.CURRENT_T3_SEND_TOOL,
    t3_thread_wait: tools.CURRENT_T3_WAIT_TOOL,
    t3_thread_read: tools.CURRENT_T3_READ_TOOL,
  },
  journalPath: verifiedHome + '/.local/share/dot-t3-monitor/completion-journal.py',
  journalDirectory: verifiedHome + '/.config/agent-kit/t3-completion',
  // Only if required by the current runtime; never bypass a denial.
  persistenceOptions: approvedPersistenceOptions,
});
const result = await runtime.runAndMonitor({
  operationId: stableOperationId,
  owner: nativeWorkerIdentity,
  method: 'launch', // or 'send'; never inferred from a response
  args: authorizedNativeArguments, // verified environmentId and clientRequestId required
  context: {
    parentTask: parentTaskIdAsString,
    acceptanceCriteria: taskAcceptanceCriteria,
    startPosition: originalReadBoundary, // -1 for no prior items; never sent to T3
  },
  ...bridge,
  monitorOptions: {timeoutMs: 60000, maxWaits: 60},
});
```

Replace the four callback placeholders with tool names discovered in the current catalog for the verified connector. Discover schema and provider/model first. The wrapper does not authorize an action or choose a provider. Preserve all user account, model, spending and runtime restrictions. Do not use a personal ChatGPT/Codex provider merely because T3 lists it.

Use the runtime's supported execution continuation for a yielded invocation. Do not end/terminate the execution while it owns active work. Tool execution itself owns the wait, not an unawaited Promise. The wrapper uses the exact native response IDs and never retries a mutation automatically. The current native launch and send schemas support `clientRequestId`, but this journal treats the request key as single-use. `resume` observes an accepted run and cannot redispatch; a different operation reusing that environment/method/request key is rejected with `request_key_in_use`. A separately authorized recovery outside this helper must not assume exactly-once deduplication.

## Ownership and recovery

The journal saves operation/request hashes, the request ID, parent task identifier, exact environment/thread/run IDs, original read boundary and progress metadata. It does not save prompts, replies, tokens or arbitrary URLs. Actual acceptance criteria remain in the parent task. This is an at-rest guarantee for the journal file only: the bridge sends the full journal request, including the launch/send message and acceptance criteria, through the existing shell command. Those values can therefore appear in shell or execution command history/logs. Never put credentials, tokens or other secrets in the native message or journal request; keep them in the existing local credential mechanism. The lease is refreshed at checkpoints and before reads; its default is five minutes. A replacement owner can claim an expired or explicitly released lease, and stale owners are fenced out.

For recovery, call `runAndMonitor` with the same operation ID, a current owner, `method:'resume'`, and the same bridge. Do not supply a new prompt or native mutation arguments. A known accepted run is observed again. Intent with a missing acceptance response returns `dispatch_uncertain`, without resending. Reconcile the existing request with a read-only `read` or `inventory`; this wrapper has no automatic or native mutation retry. A same-operation claim retains `dispatchAttempted`, and a different operation with the same request key is rejected. Treat an unconfirmed acceptance as an unresolved blocker, and do not retry dispatch unless a separate, explicitly authorized recovery establishes it is safe; that external action is not made exactly-once by this journal.

An execution budget ending returns `watch_incomplete`; keep ownership at the parent and resume this operation. An auth/permission error, pending approval/question, or broken journal is a blocker, not completion. Report the exact issue promptly and retain the unfinished record. Do not create replacement T3 work, widen access, or repair credentials as recovery.

Final result pagination is bounded by `maxPages` per pass and always starts at the immutable original `startPosition`. `lastReadPosition` records progress within that pass; it is not a safe mid-result resume cursor. Exhaustion returns `watch_blocked` with `pagination_budget_exhausted` and retains the last cursor. A resumed pass must use a larger budget and re-read from the original boundary, which may repeat reads but cannot skip final evidence. Safe mid-result resumption would require additional durable page/item evidence and is not implemented.

While a thread has a live watcher lease, a separate send operation is rejected before dispatch. Ask the existing native watcher to stop its observation, await its release, and explicitly hand ownership to the follow-up operation. Do not interrupt T3 work merely to stop observation. This implementation serializes thread operations rather than attaching concurrent sends to one watcher. Reconcile the predecessor record after a deliberate handoff; a released record alone does not establish a new active owner.

A different settled `resultRun` is not silently adopted. After independently verifying continuation lineage, resume with `continuation:{verifiedResultRunIds:[exactId],evidenceRef:authoritativeResultReference}`. The proof reference is recorded. This outside-caller wrapper never claims ownership of T3 app-owned child wake subscriptions.

The store enables recovery but does not run it. If every caller is terminated, no unattended recovery is guaranteed unless a separately authorized scheduler is actually installed and verified. No scheduler, daemon, server callback or credential was created by this implementation.

## Parent review and delivery

`ready_for_review` means coherent final evidence is available, not that acceptance criteria passed or the user received it. On a confirmed release the wrapper leaves `review_pending` with lease 0. A confirmed release is required for that handoff. The reply record must match the operation/owner/generation fence and the exact environment, thread, run, result run and review state. If the release call fails, returns a malformed or mismatched record, or its reply is lost, the wrapper returns `watch_blocked` with `releaseState:'release_uncertain'`, retains the accepted run and result evidence, and does not retry the release. The persisted record may still be `review_pending` with a live lease until expiry. Reconcile it read-only; do not force a release, redeliver or replay a batch. After a confirmed release, the parent verifies artifacts/tests, then uses the journal CLI to claim the operation with `method:'resume'` for delivery bookkeeping (do not rerun the monitor for this step):

1. `claim`: `{action:'claim',operationId,owner:parentOwner,method:'resume'}`. Retain the returned generation.
2. Before sending, `delivery` with `{operationId,owner,generation,state:'delivery_pending'}`.
3. After a confirmed accepted user-message send, `delivery` with `state:'delivered'` and its verified `receiptId` when available. An accepted send is not proof it was read.
4. If the send outcome is uncertain, record `delivery_uncertain`; do not retry blindly. Release the lease afterward.

The CLI accepts one JSON request on stdin, for example `python3 completion-journal.py --directory <verified-path>`. `read` and `list` are strictly read-only. Successful writes return `{record}`; failures return `{ok:false,error:{code}}` and exit 1. Delivery and connector-side read acknowledgments are separate.

## Optional adjacent-transition batch

A single reviewed local command can optionally execute adjacent metadata transitions through the existing `Journal.execute`: (1) `accepted` plus the initial `watching` checkpoint immediately after native acceptance, and (2) `review_pending` plus `release` at the validated terminal handoff. No native tool effect lies inside either batch. On the one-turn happy path this reduces journal commands from 9 to 7 while keeping the flattened durable transition order identical (claim, dispatching, accepted, watching, watching, watching, ready_for_review, review_pending, release).

Wire it explicitly; the one-shot path remains the default:

```js
const bridge = runtime.createToolBridge({..., batchJournalPath: verifiedHome + '/.local/share/dot-t3-monitor/completion-journal-batch.py'});
const result = await runtime.runAndMonitor({..., ...bridge, journalBatch: bridge.journalBatch});
```

The batch is **not transactional**. Steps commit independently in order, each through `Journal.execute` (own validation, lock, atomic fsync and owner/generation fence). Execution stops at the first failure; earlier steps remain committed and are never rolled back. A failed or lost reply is uncertain: the caller must reconcile with a read-only `read`, must not replay the batch, and must never retry a native mutation. The terminal batch contains `release`, so an uncertain terminal result does not trigger a second release; lease expiry remains the fence. Only `checkpoint` and `release` steps are accepted; `claim`, `delivery`, `read`, `list` and arbitrary actions are rejected.

A batch is treated as committed only when the reply proves **every** requested step: `ok === true`, `completed` exactly equals the requested step count, `results` has that same length, each result contains a record matching the operation/owner/generation fence, every requested checkpoint field (including state) or a released record with `leaseUntil === 0`, and target identity is unchanged. The wrapper repeats this validation at its entry point, including thread/run identity, preserved `startPosition`/`lastReadPosition`, `waits: 0`, `taskComplete: false` for initial watching, and `resultRunId`/review state for the terminal handoff. An injected or malformed `journalBatch` reply therefore cannot produce a false success. Initial watching writes the same metadata as the stable monitor (`threadId`, `runId`, `startPosition`, `lastReadPosition`, `waits`, `taskComplete`, `startedAt`, `observedAt`); `startedAt` and `observedAt` are the same timestamp in batch mode, whereas the stable monitor samples `now()` separately, which is semantically equivalent for watch start.

Deliberately not batched: `claim` plus dispatch intent (the intent may be required conditionally after claim, and batching it would mark dispatch on aborted or already-delivered paths), any step spanning a native call, and any fence that must follow an external wait/read. A read-only operation is never converted into a batch.

## Recovery inventory and explicit successor adoption

A replacement parent can take a **read-only inventory** without claiming a lease, creating a directory, retrying dispatch or reading result content:

```sh
printf '%s' '{"action":"inventory"}' | python3 completion-journal.py --directory <verified-journal-directory>
```

It returns exact `operationId`, method, state, owner/generation, lease expiry, environment/thread/run IDs, original run and lineage IDs, cursor, result run, handled/verified IDs, error code and delivery receipt metadata. It also reports `leaseExpired`, `leaseAvailable`, `threadBusy`, `safeToClaim`, `blockingOperationIds`, `blockingOwnerIds` and `requiredAction`. It omits request/context hashes, prompts, criteria, URLs and credentials. A live lease on an ordinary record is `leave_owner_running`; an expired lease on a thread with another live owner is `thread_busy_do_not_claim`; records in a wake state require `verify_wake_ownership_do_not_observe`. Other actions include `verify_successor_ownership_then_resume`, `review_result_do_not_redeliver`, `reconcile_uncertain_delivery`, `reconcile_exact_request` and `inspect_blocker_do_not_retry`. `safeToClaim` is limited to an expired, non-busy pre-dispatch intent; it never authorises an automatic claim or supersession.

To adopt an externally continued exact run, a parent must first establish explicit continuation evidence, then resume with that exact ID:

```js
await runtime.runAndMonitor({
  operationId: originalOperationId, owner: replacementOwner, method: 'resume',
  continuation: { verifiedResultRunIds: [verifiedSuccessorRunId], evidenceRef: authoritativeReadRef },
  adoptRunId: verifiedSuccessorRunId,
  ...bridge,
});
```

`adopt` is one atomic durable transition: it changes the watched run, resets state to `watching`, clears stale `resultRunId`, resets the read cursor and waits, and never dispatches or delivers. `originRunId` and `lineageRunIds` preserve the first run and are append-only; ordinary `checkpoint` writes to them are rejected with `lineage_controlled`. The target must already be in `verifiedResultRunIds` and the evidence reference must match. Every adoption reply is validated for complete identity, state, result clearing and lineage before any wait/read. A wait/read that merely exposes a newer run remains `result_run_changed`, and a newer active run remains `newer_work_active`; neither is adopted silently. Re-running `resume` on `review_pending` re-captures the result without setting any delivery state. An optional `instrument(event)` callback receives only `{event,at}` plus a connector method/name for `dispatch_start`/`dispatch_end` or `call_start`/`call_end`; it never receives prompts, arguments, result text or IDs, and callback errors cannot affect monitoring.
